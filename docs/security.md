# Security and local data

Bitrix MCP is local and token-free. It indexes files from configured local roots into `.bitrix-mcp/bitrix-mcp.sqlite`; keep that directory private if source paths or snippets are sensitive. File-context reads are restricted to the workspace and data directory. Project/template indexing through MCP rejects paths outside the workspace unless `BITRIX_MCP_ALLOW_OUTSIDE_WORKSPACE=1` is explicitly set. Built-in indexing ignores skip heavy or generated trees including `node_modules/`, `vendor/`, `upload/`, `cache/`, and `generated/`.

Documentation Git sources may require network during `index-docs`/`index-all` when official docs are enabled. Benchmark reporting writes JSON/Markdown reports but never deletes user data.

Live project database access is off in the server by default: the DB tools are registered only when `BITRIX_MCP_DB_ENABLED=1`. Note that `init` asks whether to enable it and defaults to **yes**, writing `BITRIX_MCP_DB_ENABLED=1` into the generated MCP config; answer no or pass `--no-db` to keep it off. `bitrix_db_query` only accepts statements that start with `SELECT`, `SHOW`, `EXPLAIN`, `DESCRIBE`, or `WITH`, and rejects multiple statements. This is a keyword check, not a database-enforced read-only mode, so it is not a security boundary: statements such as `WITH … DELETE` (MySQL 8), `SELECT … INTO OUTFILE`, or `SELECT LOAD_FILE(…)` pass it, and the query runs with the full privileges of the connection from `.settings.php`. To guarantee read-only access, point the tools at a database account that has only `SELECT` privileges (and no `FILE` privilege). `BITRIX_MCP_DB_ALLOW_WRITE=1` additionally registers `bitrix_db_execute` for arbitrary write SQL.

Credentials are read from `bitrix/.settings.php`. `bitrix_db_connections` redacts the password (it reports only whether one is set), but other tools can still expose secrets: `bitrix_read_file_context` can read any file inside the workspace, including `bitrix/.settings.php`, `bitrix/php_interface/dbconn.php`, and `.env` files; `bitrix_db_query` can read `b_user` password hashes and secrets stored in `b_option`; and `bitrix_tinker` can read anything the PHP process can. Treat everything the server can reach as visible to the AI client. These features are intended for a local development database on the same machine, never production data.

The `bitrix_tinker` tool executes arbitrary PHP with the Bitrix kernel loaded and is the most powerful capability in the server: it can run any code and modify any data, and it bypasses the read-only restrictions of `bitrix_db_query` entirely. It is off by default and only registered when `BITRIX_MCP_TINKER_ENABLED=1`. Enable it only on a trusted local development machine — never against shared or production environments. `BITRIX_MCP_PHP_BIN` should point at a PHP CLI matching the site's PHP version and extensions.
